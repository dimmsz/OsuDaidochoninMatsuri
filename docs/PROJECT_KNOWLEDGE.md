# 次回再開用プロジェクト知見

このファイルは、このリポジトリでこれまで行った実装・修正・データ整理から得た「次回も維持したい判断」と「ハマりどころ」を残すための開発メモです。

最終更新: 2026-10-10
現行アプリ表示バージョン: v1.0.13

## 1. プロジェクト概要

第47回 大須大道町人祭（2026-10-09～2026-10-11）を現地で使うPWA。

主な画面:
- NOW
- タイムテーブル
- 会場
- 検索
- お気に入り
- 出演者（独立ページ performers.html）

構成:
- フロント: 静的HTML/CSS/JavaScript
- ホスティング: GitHub Pages / Azure Static Web Apps
- DB/API: Supabase
- 地図: Leaflet + OpenStreetMap
- 徒歩ルート: Valhalla系API
- PWA: Service Worker

## 2. DBの基本設計

主なテーブル:
- festivals
- venues
- events
- event_tags
- performers
- event_performers
- map_styles

イベントの考え方:

events.performer は表示用の元文字列として残す。
performers / event_performers は出演者マスター・正規化用。
events.title は演目名。
したがって「出演者」と「演目名」は同じものとして扱わない。

出演者は多対多:
- 1イベントに複数出演者
- 1出演者が複数イベントに出演

## 3. 会場モデルは「親会場」と「区画」を分ける

重要:

- 実在する物理的な固定場所 = venues
- 公式タイムテーブル上の会場内区分 = events.venue_section

例: 大須観音は地図上では1会場だが、公式タイムテーブルでは
- 西門
- プロレス
- 中
- 東
に分かれる。

このため、新しい区画を見つけたときに安易に別venueを作らない。

裏門前町も同様に、公式タイムテーブルに合わせて
- 北
- 中央
- 南
の3区分として扱っている。

## 4. 固定会場・ロービング・移動演目

イベントの場所は3種類で考える。

### 固定会場
- location_type = fixed
- venue_id = 実在会場ID
- 必要なら venue_section

### ロービング
- location_type = roaming
- venue_id = NULL
- location_label = ロービング

ロービングは固定地点ではないため、原則として venues に地図上の固定会場として登録しない。

### 移動演目・行進
- location_type = route
- venue_id = NULL
- location_label = 移動演目

「複数の会場列を横断する」「行進しながら行う」演目は、特定venueに重複登録せず、1イベントで表す。

今回の代表例:
- ラクダ ラクダ対決！
- 2026-10-10 17:00～17:20
- event id 232
- location_type = route
- location_label = 移動演目
- genre = 特別企画
- event_type = special
- venue_id = NULL

公式タイムテーブルで複数会場列にまたがる表現になっていても、同一演目ならDB上は1イベントを基本とする。

画面表示:
- 固定会場: 📍 大須観音・東
- ロービング: 🌀 ロービング
- 移動型: ↔ 移動演目

## 7. ジャンルとタグの原則

ジャンルは比較的「狭く・代表的に」。
タグは「広く・検索しやすく」。

つまり:
- genre = 主ジャンル
- event_tags = その演目の特徴を横断的に付与

「大道芸」を全員の代表ジャンルにするのではなく、分かるなら具体的なジャンルを優先。

## 10. お気に入りの仕様

localStorage key:
osu-favorites

タイムテーブル、NOW、検索、お気に入り、出演者ページで共通利用。

## 11. お気に入りの時間重複警告

お気に入りイベント同士について、同日かつ時間帯が重なる場合を検出する。

判定は:
start(x) < end(y) && start(y) < end(x)

重複イベントには:
- .event-conflict
- ⚠ 時間重複
を表示。

現在のUI方針:
- EDCBのように、見落としにくく強めに警告
- ただし時刻や日付の上に警告を重ねない
- 左側の強いオレンジ系ボーダー + 警告pillを使う
- .event の共通カードを壊さない

この処理はお気に入り画面専用の付加表現で、NOWの開催中表示とは別。

## 12. NOW / 開催中表示での注意

お気に入り一覧は card(e, false, true) のように「お気に入り画面用」で描画し、NOWのlive表示を誤って引き継がない。

過去に「未来のイベントなのに開催中表示になる」問題があり、主因の一つが古いJS/SWキャッシュだった。

したがって、描画条件だけでなく、Service Workerとアセットversionも必ず確認する。

## 13. PWAキャッシュで最も重要な知見

過去にcache-firstのため、コードを更新したのにブラウザに古いJSが残る問題が発生した。

現在は network-first:
1. ネットワーク取得を試す
2. 成功したらキャッシュを更新
3. ネットワーク失敗時だけ既存キャッシュを使う

現行:
- cache name: osu-now-v36
- app version: v1.0.13
- app.js / style.css に ?v=1.0.13

UIや取得ロジックを更新したときは、次の3つをセットで確認する:
- index.html のversion
- app.js/style.css のquery version
- sw.js のCACHE名

Service Workerの古いキャッシュ問題を疑う場合は、まず実際に配信されている sw.js と app.js のversionをブラウザで確認する。

## 14. Azure Static Web Apps のデプロイでの注意

過去に古いデプロイが後から反映され、最新変更が戻ったように見える問題があった。

GitHub Actionsでは同時実行を防ぐため、workflowに次を入れている:

~~~yaml
concurrency:
  group: azure-static-web-app-${{ github.ref }}
  cancel-in-progress: true
~~~

Azure側だけでなく、GitHub Actionsの実行履歴も確認する。

「GitHub mainにはあるのにAzureだけ古い」場合は、
- Actionsの実行順
- どのcommitがdeployされたか
- Service Workerのキャッシュ
を順番に確認する。

## 15. UIを変更するときの注意

.event は NOW / タイムテーブル / 検索 / お気に入りで共有されている共通カード。

したがって、.event 自体を大きく変更すると複数画面に影響する。

画面固有の装飾は、
- .event-now
- .event-conflict
などの追加classで行う。

「お気に入りだけ変更したつもりなのにNOWまで変わった」場合は、共通CSS/共通card描画を疑う。

## 16. 出演者ページのAPI取得での注意

出演者検索には少なくとも:
- id
- name
- genre
- description

を取得する必要がある。

以前 id,name だけ取得していたため、genre pickerが空になる問題があった。

genre filterを追加・変更するときは、APIのselect列も一緒に確認する。

## 17. 公式タイムテーブルPDFを扱うときのルール

公式PDFの見た目をそのままDB行に変換しない。

まず確認する:
1. 日付
2. 時刻
3. 会場名
4. 会場区画
5. 出演者
6. 演目名
7. その演目が固定会場か、ロービングか、移動型か
8. 同一演目が複数列にまたがっていないか

特に複数会場列にまたがる演目は、同じイベントをvenueごとに複製しない。

今回の「ラクダ ラクダ対決！」がこの典型。

## 18. 現在の運用方針

データ変更後は「入力して終わり」にせず、SQLで次を確認する:
- 件数
- eventとperformerの関連
- event_tagsの付与状況
- venue_id / venue_section
- location_type / location_label
- genreの整合性

同じ出演者・同じ演目の公演を追加するときは、既存公演のtagを参照してから登録する。

## 19. 次回再開時の最初の確認手順

1. README とこのファイルを読む
2. mainの最新commitを確認
3. index.html のアプリversion確認
4. sw.js のCACHE名確認
5. Azure Actionsの最新deploy確認
6. Supabaseの現行schema/件数確認
7. 公式タイムテーブルの最新版がある場合は、そのPDFを一次資料として確認

## 21. 「迷ったらこの原則」で判断

- 公式タイムテーブルを最優先
- 固定場所はvenue、区画はvenue_section
- 移動型はvenueを無理に付けない
- genreは狭く、tagは広く
- 出演者と演目は分離
- 同じ出演者・同じ演目はtagをそろえる
- 共通カードの変更は全画面への影響を考える
- PWA変更時はversion/cache/deployをセットで確認
- 根拠がない情報を推測でDBに入れない

### 今回確認した重要なルール

1. `events.performer` の共演表記を、機械的に出演者マスター名へ変更しない。
2. `event_performers` は多対多の関連テーブルなので、`events.performer` と完全一致しないことだけでマスターを未使用扱いしない。
3. 明確な誤記・重複などの根拠がない限り、出演者マスターを削除しない。
4. ユーザーがひとまとまりとして残すと判断した共演表記は分割しない。
5. 共演表記の区切り文字は `／` に統一する。
6. 表記整理は候補ごとに確認してから変更し、判断結果を記録する。
